# /spec

Нетривиальная задача проваливается не на коде, а раньше: агент понял иначе, чем человек,
и это выясняется после реализации. Скилл разворачивает работу в четыре шага — контекст,
ТЗ через вопросы, прототип без кода, код — и ставит письменное согласие человека между
третьим и четвёртым.

## Когда применять

Порог: задача крупнее точечной правки.

Применять — новая функциональность, смена поведения, интеграция с внешней системой,
всё, что затрагивает несколько модулей или не закрывается за одну сессию.

Не применять — правка в одну строку, багфикс с ясным воспроизведением, переименование,
обновление документа. Такое ведётся по `AGENTS.md`, раздел «4. Работа от проверяемой цели».

Непонятно, по какую сторону порога задача, — спросить одной строкой: «делаем ТЗ или сразу?»

## Вход

Черновой план человека, 3–10 строк: чего он хочет, своими словами. Плана нет — попросить
его, а не выдумывать за человека. Из «сделай хорошо» ТЗ не выводится, а угаданная цель
обходится дороже вопроса.

## Шаг 1. Контекст из репозитория

Прочитать **до первого вопроса**: `agent_docs/snapshot.md`, `agent_docs/backlog.md`,
`agent_docs/architecture.md`, `agent_docs/invariants.md`, релевантные ADR
(`agent_docs/adr/`) и код по теме задачи.

Вопросы, на которые отвечает репозиторий, человеку не задавать. Каждый такой вопрос —
признак, что шаг 1 пропущен.

## Шаг 2. Вопросы → ТЗ

Завести файл ТЗ сразу: `agent_docs/specs/YYYY-MM-DD-<slug>.md` по шаблону
`agent_docs/templates/spec.md`, статус «черновик», исходный план — дословно.

Спрашивать по 1–3 вопроса за раунд, каждый — с вариантами ответа. В Claude Code —
инструментом AskUserQuestion; где его нет (Codex, Cursor) — нумерованным списком в чате,
варианты буквами.

О чём спрашивать:

| тема | что выясняем |
|---|---|
| цель | что изменится для пользователя и по какому признаку это видно |
| границы | что в задачу **не** входит |
| сценарии | кто и как этим пользуется, включая крайние случаи |
| ограничения | инварианты, интеграции, формат данных, сроки |
| приоритеты | чем жертвуем, когда требования конфликтуют |

Ответ записывать в ТЗ сразу, в раздел «Вопросы и ответы», а не в конце: сессия обрывается,
и незаписанный ответ спрашивают повторно.

Остановка: раздел «Критерии приёмки» пишется без догадок. Раундов — не больше пяти;
оставшееся уходит в «Открытые вопросы», работа идёт дальше.

## Шаг 3. Прототип без кода

Показать решение так, чтобы человек увидел его до реализации. По типу задачи:

| тип задачи | что показать |
|---|---|
| UI | макет экранов текстом или ASCII (можно mermaid), состояния, тексты кнопок и ошибок |
| API | сигнатуры, примеры запроса и ответа, коды ошибок |
| данные | схема таблиц и сущностей, что мигрирует и как |
| процесс, интеграция | диаграмма последовательности: кто кого вызывает и в каком порядке |

Прототип живёт в разделе «Прототип без кода» файла ТЗ.

На этом шаге **не создавать и не править файлы кода, не ставить зависимости.** Прототип —
текст; вся его ценность в том, что его дёшево выбросить.

Показать человеку и спросить, что не так. Шаги 2 и 3 повторять, пока не прозвучит явное
«согласовано». Кругов — не больше трёх; дальше записать разногласия в «Открытые вопросы»
и спросить, идти ли в код с ними.

## Шаг 4. Передача в код

1. Статус ТЗ → «согласовано».
2. В `agent_docs/backlog.md`, раздел Next — пункт со ссылкой на файл ТЗ.
3. План реализации с проверками (`AGENTS.md`, раздел «4. Работа от проверяемой цели») записать в ТЗ, а не держать в голове.
4. Критерии приёмки превратить в тесты: один критерий — один проверяемый тест.
5. Реализация завершена, когда тесты написаны и проходят (`agent_docs/guides/dod.md`).

## После реализации

- Статус ТЗ → «реализовано».
- В записи `agent_docs/development-history/` — ссылка на файл ТЗ.
- Важные развилки, всплывшие по ходу, — отдельным ADR (шаблон `agent_docs/templates/adr.md`).
- ТЗ задним числом не переписывать. Разошлось с реализацией — в раздел «Отклонения при
  реализации»: что сделано иначе и почему. Подчищенное ТЗ врёт о том, что знали на момент
  согласования.

## Чего не делать

- Не писать код до явного «согласовано».
- Не задавать вопросы, ответ на которые есть в репозитории.
- Не сваливать всё ТЗ в один вопрос-простыню: на простыню отвечают «да, норм».
- Не превращать ТЗ в архитектурный документ. Долговечное — в `agent_docs/architecture.md`
  и `agent_docs/adr/`; в ТЗ — одна задача.
