# Инварианты продукта

Жёсткие правила продукта, которые нельзя нарушать. Не стиль, не предпочтение — нарушение инварианта = баг.

Отличие от правил в `AGENTS.md`: там — как работает **агент**, здесь — что не должно произойти с **продуктом** (данные, безопасность, контракты).

Если инвариант мешает задаче — это не повод его нарушить, а повод обсудить: либо ослабить формулировку (с записью причины в «История»), либо изменить задачу.

**Категории (подсказка):** `data` · `security` · `api` · `performance` · `migration` · `compatibility` · `pii`

---

## INV-001: Секреты не попадают в git

**Категория:** security
**Правило:** Пароли, токены, ключи, connection strings — только в `.env` (gitignored) или секрет-хранилище. В коде и коммитах — только имена переменных.
**Почему:** Утечка секрета из истории git компрометирует все зависящие системы. Удаление из истории постфактум ненадёжно.
**Как проверить:** ревью diff перед коммитом; `.env*` в `.gitignore` (кроме `.env.example`).
**История:** —

## INV-002: Пароли и credentials не пишутся в логи

**Категория:** security / pii
**Правило:** В логи не попадают пароли (в т.ч. неверные при неуспешном входе), токены, сессионные куки, хэши паролей.
**Почему:** Логи реплицируются и читаются широким кругом; неверный пароль пользователя часто отличается от верного на один символ.
**Как проверить:** ревью кода логирования на auth-путях; grep по логам тестового стенда после прогона E2E.
**История:** —

## INV-003: Деструктивные миграции запрещены

**Категория:** data / migration
**Правило:** Миграции схемы — только через `ALTER`, `ADD`, `RENAME`, `CREATE` или дополнительные таблицы. `DROP TABLE`, `TRUNCATE`, `DELETE FROM` без `WHERE` в коде миграций запрещены.
**Почему:** Потеря продакшн-данных невосстановима.
**Как проверить:** ревью каждой миграции; `grep -rE 'DROP TABLE|TRUNCATE|DELETE FROM' migrations/` пуст.
**История:** —

## INV-004: IP клиента за прокси берётся из доверенного источника

**Категория:** security
**Правило:** Если приложение стоит за реверс-прокси, клиентский IP определяется только тем
элементом заголовка, который добавил САМ прокси (при одном доверенном прокси — **правый** элемент
`X-Forwarded-For`). Брать левый элемент, «первый публичный» или доверять `X-Real-IP` без гарантии
перезаписи на прокси — запрещено.
**Почему:** большинство прокси (в т.ч. nginx с `$proxy_add_x_forwarded_for`) ДОПИСЫВАЮТ присланный
клиентом заголовок к реальному адресу — левые элементы полностью контролирует атакующий. Следствия:
обход rate-limit (DoS, а если по IP лимитируется отправка SMS — прямые деньги), подделанный IP в
доказательных документах и в аудите (расследование уводится в ложную сторону).
**Как проверить:** тест «клиент прислал свой XFF → приложение видит адрес прокси-хопа, а не
подставленный»; ручная проверка с ЛИЧНОГО компьютера (не с сервера — оттуда запрос идёт с
приватного адреса и может попасть под доверие прокси):
`curl -s https://<хост>/<эндпоинт-с-логом-IP> -H "X-Forwarded-For: 203.0.113.77"`.
**История:** сеть ШЦТ, 2026-07-25 — подделка подтверждена на проде у двух сервисов сразу; правка
на уровне прокси лежала в образе (не в томе) и откатывалась при пересоздании контейнера, поэтому
защита в приложении обязательна независимо от инфраструктуры.
